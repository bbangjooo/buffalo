# Byeong-geun Jo · bbangjo

A personal Three.js space introducing Byeong-geun Jo through music, travel, reflections and play. Four rooms extend into open low-poly meadows with 13 objects and panels: a coffee panel, five piano pieces, six blog posts and a guestbook. The house and meadows share one continuous scene. The original robot guides visitors through the rooms; a separate giant smooth plush hamster lives in the About meadow and dances at normal size in the rhythm game. Visitors explore the meadows in first person.

## Run

```sh
npm ci
npm run dev
npm run build
npm run preview
```

Use Node.js 24. The existing Vercel project `buffalo` deploys `main` automatically to [bbangjo.kr](https://bbangjo.kr). `vercel.json` configures Vite, `npm ci`, `npm run build` and the `dist` output. For a manual production deployment, run `sh build.sh` from the repository root. `.vercelignore` excludes authoring assets, design references and scripts from the deployment upload.

## Guestbook storage

The deployment now includes awaited Vercel Function entry points at `api/guestbook.js` and `api/leaderboard.js`. They use the private **buffalo-community** Vercel Blob store in **icn1**, through `@vercel/blob` 2.8.0. Production uses `community/` objects; Vercel Preview uses separate `community-preview/` objects. Production was deployed and verified on 2026-09-10: both live GET routes return JSON200, the migrated guestbook displays its preserved entry, and retained-ID POST retries return200 without adding a duplicate. New submissions, score derivation and fresh reads were verified in the isolated Vercel Preview namespace before release.

`GET /api/guestbook` returns the latest 200 entries. `POST /api/guestbook` accepts `{ author, body, submissionId? }`, with a 24-character name and 120-character message. The UI keeps the same UUID and normalized draft when retrying an uncertain response. A retained ID returns the original entry; conflicting content is rejected. Meaningful edits or a confirmed success start a new submission identity. Failed saves preserve the draft and never display a false success notice.

Local `npm run dev` and `npm run preview` still use `.local-data/guestbook.json` and `.local-data/leaderboard.json`, with optional `GUESTBOOK_DATA_FILE` / `LEADERBOARD_DATA_FILE` paths. Vite preview is distinct from a Vercel Preview deployment. Local files remain untouched by normal Blob operation and excluded from Git and Vercel uploads. Browser-local preferences are not a substitute for shared entries.

## Leaderboard storage

Finished runs offer **Name** and **Submit score**. Play's framed `/leaderboard.html` document shows rank, name, score, accuracy and combo, with English loading, empty, error, refresh and retry controls. The **Leaderboard** room button and wall click focus that document; **Back to room / Esc** returns to Play. Among the common room action buttons, only **Rhythm game** uses the primary accent style. `LeaderboardScreen.ts` keeps the document mounted as a CSS3D surface and requests scores when Play becomes active, when the visitor refreshes, or after a confirmed score update. Updates received while inactive wait until the screen is active. `GET /api/leaderboard` returns ranked current-track entries; `POST /api/leaderboard` accepts `{ runId, name, trackId, perfect, great, good, misses, maxCombo }` and returns `{ entry, rank, saved, duplicate }`. The shared types live in `src/design/leaderboard.ts`.

The current track, **Lasso Lady** (`lasso-lady-four-key-v1`), retains its top 200 runs, sorted by score, accuracy and maximum combo descending, then creation date and ID ascending. Stored runs for the earlier Beethoven Virus track remain under their original track ID and note count; they are excluded from the current table and are preserved when a new Lasso Lady score is saved. Different runs may use the same name. Identical retries of a retained run UUID return the existing entry; conflicting payloads are rejected. There is no permanent receipt for evicted or unqualified runs. The UI keeps an uncertain request’s complete payload stable and reports an unqualified score as not ranked.

The server derives score and accuracy from validated judgement counts and the chart length, including feasible combo bounds. Gameplay itself is client-reported and not authoritatively verified. There is no account authentication or anti-cheat claim. The two-second per-IP check is best-effort memory within a Function instance, not a global abuse limit.

The Blob driver reads uncached private content and updates documents with ETag preconditions. A conflicting write retries the same pure mutation against a fresh version instead of overwriting another visitor’s changes. The migration script `scripts/migrate-community-data.mjs` copies nonempty local documents only into empty production collections, treats identical existing content as a no-op and refuses differing existing records. It verifies remote content and preserves local bytes.

The configured Vercel team is on Hobby. Its included Blob allowances are 1 GB storage, 10,000 reads, 2,000 write/list operations and 10 GB transfer; exhausted Hobby limits can make Blob unavailable rather than incur paid overage. See the [official usage and pricing](https://vercel.com/docs/vercel-blob/usage-and-pricing) and `design/community-storage.md` for the environment boundaries, concurrency, migration and rollback details. Serving only `dist/` without the Function routes does not provide these APIs.

Run `node scripts/verify-guestbook.cjs`, `node scripts/verify-leaderboard.cjs`, `node scripts/verify-community-api.cjs` and `node --test scripts/verify-blob-document.mjs` for isolated local and Blob-driver checks. Live preview/production verification is separate from those tests.

## Sampled piano sound

The instrument uses Alexander Holm’s **Salamander Grand Piano V3** recordings of a Yamaha C5 under **CC BY 3.0**, with two velocity layers and 60 MP3 samples totaling **5,966,897 bytes** (about 5.97 MB). The bank loads when the piano is requested. Soft and bright recordings vary the timbre with note velocity; their recorded attack, stereo resonance and decay replace the former oscillator sound. A short damped release and quiet room reverb complete the sound. There is no oscillator fallback on load failure.

Sample adaptations and full acquisition/license evidence are recorded in `design/piano-audio.md`. The header's **Information → Credits** menu opens `/audio/piano/index.html` in a new tab, with keyboard navigation and focus restoration. The explicit filename reaches the attribution page in Vite development as well as the static build; sample assets and license files remain in `/audio/piano/`. The transport retains the authored pitches, note durations, sustain durations, timing and key animation. Reference YouTube performances are separate from this licensed sample bank. Run `node scripts/verify-audio-channels.cjs` and `node scripts/verify-piano-performance.cjs` for sample integrity, cancellation and original performance scheduling.

## Score playback

Configuration: `src/design/piano-performance.ts`. The performance uses the user-provided nine-page *En avril, à Paris* PDF, credited to Charles Trenet / Alexis Weissenberg, realized by Ryo.K from M-A Hamelin's recording and edited/typeset by Shota Ezaki. All 144 measures were manually checked after local optical recognition, with 1,796 reviewed source events becoming 1,747 audible attacks after tied notes and a shared unison are merged. The rendered performance lasts about 3:40. Reviewed corrections and the performance audit are included under `assets/music-transcription/`; page renders, OMR drafts, extraction ledgers and logs remain local and are excluded from Git and deployment. The original PDF is preserved outside the repository.

Regenerate the timed score with `python3 scripts/music/build_performance.py`. `assets/music-transcription/performance-audit.json` traces every source event to the timed output. The initial quarter-note tempo of approximately 152 comes from the score; numerical rubato, fermata, ornament, rolled-chord and velocity settings are documented performance choices. The source's m83 octave annotation and the inferred m143 tuplet ratio remain explicitly recorded.

`PianoPerformance.ts` schedules notes against the same WebAudio clock used to animate keys. Audio retains the score's original pitches, including notes outside the stylized model's visible two-octave range; only existing matching keys move. The audio engine supports 64 simultaneous voices. Playback schedules real Salamander Grand Piano samples from the score data. It is not a recording of someone performing this arrangement.

The audio engine distinguishes scheduled score voices from manual/game interactions. `stopInteractiveNotes()` cancels only the latter, including pending manual requests, so room cleanup cannot interrupt a running or starting performance. Verify that separation with `node scripts/verify-audio-channels.cjs`.
